# Transaction Ledger API

A backend API for a simple transaction ledger. Users can create accounts, record credit and debit transactions, check balances, view paginated transaction history, and transfer money between accounts (bonus).

Built with **FastAPI**, **PostgreSQL** and **raw SQL via psycopg v3** (no ORM).

## Features

- **Create account**: id and `created_at` are generated by the system; the balance always starts at `0.00`.
- **Add transaction**: credit or debit, with the balance updated in the same database transaction.
- **Duplicate protection**: the same `reference_id` cannot be used twice on the same account.
- **Get balance**: returns `account_id` and `balance`, or 404 if the account does not exist.
- **Transaction history**: filter by type, page/limit pagination, latest first.
- **Money transfer (bonus)**: debit one account and credit another atomically.
- **Immutability**: there are no update or delete endpoints for transactions.

## Local Setup

### Prerequisites
- Python 3.10 or newer (the code uses `str | None` type syntax)
- PostgreSQL 18 or newer, running locally

### 1. Create a virtual environment and install dependencies
```bash
python -m venv .venv
# Windows:    .venv\Scripts\activate
# Mac/Linux:  source .venv/bin/activate

pip install -r requirements.txt
```

### 2. Create the database
Create an empty database, for example `transaction_ledger`, in PostgreSQL.

### 3. Configure the environment
Create a `.env` file in the project root:

```env
DATABASE_URL=postgresql://postgres:YOUR_PASSWORD@localhost:5432/transaction_ledger
```

> If your password contains special characters, URL-encode them (for example `@` becomes `%40`).

### 4. Create the tables
```bash
python -m modules.db.init_db
```
This runs `CREATE TABLE IF NOT EXISTS` for `accounts` and `transactions`, so it is safe to run more than once.

### 5. Start the server
```bash
uvicorn main:app --reload
```

### 6. Open the interactive docs
- Swagger UI: http://127.0.0.1:8000/docs
- ReDoc: http://127.0.0.1:8000/redoc

## Design Decisions and Reasons

### Raw SQL instead of an ORM
Every query is visible and uses parameter placeholders, so there is no SQL injection risk from user input. It also makes locking behaviour (`FOR UPDATE`) explicit and easy to reason about.

### Layered structure (routes → service → repository → schema)
Routes only deal with HTTP, services hold the business rules, and repositories hold the SQL. Rules can be changed without touching the queries, and the structure is the same for both features.

### Atomicity: one database transaction per request
Each request gets one connection from the pool through `get_connection`. With psycopg, `with pool.connection()` commits when the block ends normally and rolls back if an exception escapes. The transaction insert and the balance update therefore commit together, or not at all. For transfers, both inserts and both balance updates share the same database transaction, so a partial transfer cannot be persisted.

### Concurrency: row locks with `SELECT ... FOR UPDATE`
Before reading a balance to decide on a debit, the account row is locked. Two simultaneous debits on the same account run one after the other, and the second sees the updated balance. This prevents two requests from both passing the balance check against the same old balance.

### Deadlock prevention for transfers
Transfers lock both accounts in one query with `ORDER BY id ASC FOR UPDATE`. Every transfer locks rows in the same order (ascending id), so two opposite transfers (A→B and B→A) at the same time cannot deadlock. Because ids are UUIDs, this is a consistent ordering rather than a meaningful alphabetical one.

### Duplicate handling

The duplicate check runs after the account row is locked, so concurrent requests with the same `reference_id` on one account are serialised and the second one is rejected with 409. The database constraint `UNIQUE (account_id, reference_id)` is the final safety net.

For transfers, the same `reference_id` is written to both the debit row (source account) and the credit row (destination account). The duplicate check therefore looks at both accounts `(account_id IN (source, destination))`, so a clash on either side is rejected up front with 409 instead of failing on the database constraint halfway through.

### Database constraints as a safety net
| Constraint | Purpose |
|---|---|
| `accounts.balance CHECK (balance >= 0)` | the balance can never go negative, even if application code has a bug |
| `accounts.name CHECK (trim(name) <> '')` | no blank names |
| `transactions.type CHECK (type IN ('credit','debit'))` | only valid types |
| `transactions.amount CHECK (amount > 0)` | no zero or negative amounts |
| `UNIQUE (account_id, reference_id)` | no duplicate transactions per account |
| `account_id REFERENCES accounts(id) ON DELETE RESTRICT` | an account with transactions cannot be removed |
| `NOT NULL` on required columns | no missing data |

### Money handling and JSON Serialization
All amounts and balances are handled as Python `Decimal` and stored as `NUMERIC(15, 2)`. Binary floating point cannot represent many decimal values exactly (`in Python, 0.1 + 0.2 gives 0.30000000000000004`), which could introduce small errors into balance arithmetic. `Decimal` is exact, and `NUMERIC(15, 2)` fixes the scale at two decimal places.

JSON Format: Pydantic v2 serializes `Decimal` to JSON Strings (`e.g., "balance": "0.00"`). This prevents frontend JavaScript engines from parsing the numbers as float and losing precision.


### Immutability
The API exposes no endpoint to update or delete a transaction. This is enforced at the API level only; there are no database triggers or permission restrictions.

### Stored balance plus transaction rows
The balance is stored on the account and updated in the same database transaction as each ledger row, so reads are fast. Because both writes are atomic and happen under the row lock, the balance equals the net of all valid transactions.

### Latest-first ordering
Results are ordered by `created_at DESC, id DESC`. `created_at` uses the database's `CURRENT_TIMESTAMP`, which is the start time of the database transaction. Rows created in the same database transaction (the two rows of a transfer) share a timestamp, and the `id` tie-breaker is only for a stable order, not a chronological one.

### Pagination
Uses `LIMIT`/`OFFSET`. The response includes `page`, `limit`, `total_records` and `total_pages`, as the assignment requires. `limit` is capped at 50 to avoid very large responses.

### Connection pool
`psycopg_pool.ConnectionPool` (1 to 15 connections) is opened when the app starts and closed when it stops. If the database cannot be reached or the pool times out, the API returns 503.
